## Pain Points & Inefficiencies

### 🔴 Critical Issues

#### 1. **Dual-Path Data Loading Creates Confusion**

**Problem:**
- `getScheduleTasks()` has TWO completely different code paths
- If To Do List is empty → reads source sheets directly via `collectAndGroupTasks()`
- If To Do List exists → reads from To Do List sheet and INFERS source
- Source inference is error-prone (matching keywords in taskType)

**Why This Hurts:**
- Developers must maintain two separate parsing logics
- Bug fixes must be applied in both paths
- Different code paths may return slightly different data structures
- Users don't understand when To Do List needs regeneration

**Current Workaround:**
- TripPlanner bypasses this by ALWAYS reading source sheets directly
- ToDoSchedule uses the dual-path approach
- TimeBreakdown only reads To Do List (no fallback)

#### 2. **localStorage State Diverges from Server State**

**Problem:**
- Five separate localStorage keys track task state:
  - `rubberTracker_personalChecklist` - Which tasks user claimed
  - `rubberTracker_notifiedTasks` - Which tasks user sent SMS for
  - `rubberTracker_scheduledTasks` - Which tasks user scheduled classes for
  - `rubberTracker_officeTasks` - Which tasks are office work
  - `rubberTracker_classTypeTasks` - What class type user selected
- These are keyed by: `employee + '|' + taskType + '|' + itemType`
- If employee name changes in Employees sheet → localStorage orphaned
- If task regenerated with different itemType → localStorage orphaned
- No expiration or cleanup mechanism

**Why This Hurts:**
- User sees "Notified" badge on task that was deleted and recreated
- User's checklist contains tasks that no longer exist
- No way to sync state across devices/browsers
- State persists forever (even for Previous Employees)

**Example Failure Scenario:**
```
Day 1: User adds "Joe Smith - Renew CPR" to checklist (localStorage)
Day 2: Joe Smith renamed to "Joseph Smith" in Employees sheet
Day 3: User opens ToDoSchedule → Task appears in both Task List AND My Checklist (duplicate)
       Because localStorage key uses old name, isTaskInChecklist() fails to match
```

#### 3. **To Do List Sheet Purpose is Unclear**

**Problem:**
- To Do List is described as "aggregated schedule view"
- But TripPlanner doesn't use it (reads sources directly)
- ToDoSchedule can work without it (fallback to source reading)
- TimeBreakdown requires it
- Generated by `generateSmartSchedule()` but users don't know when to regenerate
- Contains calendar section (rows 1-12) but calendar is always outdated

**Why This Hurts:**
- Users confused about when/why to run "Generate Smart Schedule"
- To Do List becomes stale (shows old dates, completed tasks)
- Calendar section in To Do List never matches dialog calendar
- Unclear if To Do List is "working storage" or "historical record"

#### 4. **Phone Number Lookup is Overly Complex**

**Problem:**
- Phone numbers stored in Employees sheet
- Loaded into `employeePhones` map keyed by lowercase name
- 3-level fallback matching:
  1. Exact match (normalized whitespace)
  2. Remove parentheses: "John Smith (AP 3)" → "John Smith"
  3. Partial match: Find firstName + lastName anywhere in keys
- This runs for EVERY task, EVERY time dialog opens
- Phone numbers also stored in localStorage checklist items (can be stale)

**Why This Hurts:**
- Performance: O(n²) partial matching on large employee lists
- Fragile: Breaks if employee has nickname, middle name, suffix
- Duplication: Phone numbers in Employees sheet + localStorage + allTasks array
- No validation: Can store invalid phone numbers

### 🟡 Medium Issues

#### 5. **Manual Tasks Sheet is Overloaded**

**Problem:**
- Stores user-created calendar tasks
- Stores office work entries
- Stores trip plan applications
- Has flexibility columns (Locked, Allow Day Change, etc.) for trip planning
- Mixed with personal checklist items (via localStorage)

**Why This Hurts:**
- Hard to distinguish "real" manual tasks from system-generated entries
- Flexibility columns only used by TripPlanner (wasted space for user tasks)
- No clear ownership: Is this user's personal list or system schedule?

#### 6. **Foreman Information Embedded in Location String**

**Problem:**
- Tasks store location as: `"Bozeman (👷 John Smith)"`
- Foreman extracted via regex: `/\(([^)]+)\)$/`
- If location string format changes, grouping breaks
- Can't easily filter by foreman without parsing strings
- Emoji makes string matching fragile

**Why This Hurts:**
- String parsing is slow and error-prone
- Can't do database-style queries: "Show all tasks for Foreman X"
- Emoji encoding issues in some environments
- Harder to maintain/refactor

#### 7. **Status Tracking is Scattered**

**Problem:**
- Task status in multiple places:
  - `allTasks[i].status` - In-memory (Pending/Complete/Scheduled/Overdue)
  - `notifiedTasks[key]` - localStorage boolean
  - `scheduledTasks[key]` - localStorage boolean
  - `officeTasks[key]` - localStorage boolean
  - Source sheet status column (if exists)

**Why This Hurts:**
- No single source of truth for task state
- Difficult to query: "Show all tasks I've notified but not scheduled"
- State can be inconsistent (task marked Complete but still in notifiedTasks)

### 🟢 Minor Issues

#### 8. **Task Deduplication Logic is Fragile**

**Problem:**
- `isTaskInChecklist()` matches by: employee + taskType + itemType
- What if two employees have same name? (Unlikely but possible)
- What if same employee has two glove swaps same day? (Different item numbers)

#### 9. **Column Header Detection is Brittle**

**Problem:**
- To Do List reading uses string matching: `header.indexOf('scheduled date')`
- If column renamed or language changed, breaks silently
- No validation that required columns exist

#### 10. **No Data Version Tracking**

**Problem:**
- localStorage has no version number
- If data structure changes, old localStorage causes errors
- No migration path for schema changes

## Proposed Architecture Options

### Option A: Eliminate To Do List Sheet (Single Source of Truth)

**Concept:** Remove To Do List intermediate sheet entirely. All dialogs read directly from source sheets.

**Architecture:**
```
Source Sheets (Glove Swaps, Sleeve Swaps, etc.)
    ↓
    ONLY collectAndGroupTasks() [76-SmartScheduling.gs]
    ↓
HTML Dialogs (ToDoSchedule, TripPlanner, TimeBreakdown)
    ↓
[Server-Side Storage]
    - Task Metadata sheet (new) - stores scheduledDate, status, notified flags
    - Employee sheet - master data
    - Manual Tasks - user-created tasks only
```

**Task Metadata Sheet Structure:**
| Employee | TaskType | ItemType | SourceSheet | SourceRow | ScheduledDate | Status | NotifiedDate | ScheduledClassDate | ClassType | IsOffice | Notes |
|----------|----------|----------|-------------|-----------|---------------|--------|--------------|-------------------|-----------|----------|-------|
| John Smith | Swap | Glove | Glove Swaps | 15 | 2026-02-05 | Pending | 2026-01-28 | 2026-02-10 | Online | FALSE | ... |

**Pros:**
- ✅ Single code path (no dual-path confusion)
- ✅ Source sheets remain authoritative
- ✅ Task state stored server-side (no localStorage sync issues)
- ✅ Can query task state with sheet formulas
- ✅ State shared across devices automatically
- ✅ Clear separation: source data vs. metadata

**Cons:**
- ❌ Requires new sheet creation
- ❌ Migration needed for existing localStorage data
- ❌ More server reads/writes (potential performance impact)
- ❌ Task Metadata sheet can get large (one row per task instance)
- ❌ Need garbage collection for old completed tasks

**Implementation Complexity:** 🔴 High (3-4 weeks)

---

### Option B: Clarify To Do List as Working Schedule (Current + Refinements)

**Concept:** Keep To Do List but clarify its purpose and fix the dual-path issue.

**Architecture:**
```
Source Sheets
    ↓
generateSmartSchedule() - User runs manually
    ↓
To Do List sheet - "Working Schedule" (users understand it's a snapshot)
    ↓
HTML Dialogs READ from To Do List ONLY (remove fallback path)
    ↓
Write back: scheduledDate, status updates
    ↓
[NEW] ScriptProperties stores:
    - notifiedTasks JSON
    - scheduledTasks JSON
    - officeTasks JSON
    (keyed by: sourceSheet + sourceRow for stability)
```

**Changes:**
1. Remove "read directly from source sheets" fallback in `getScheduleTasks()`
2. Force users to run "Generate Smart Schedule" if To Do List is empty
3. Add "Last Generated" timestamp to To Do List
4. Add "Refresh" button that re-runs `generateSmartSchedule()`
5. Move localStorage state to ScriptProperties
6. Change localStorage key from employee+taskType to sourceSheet+sourceRow

**Pros:**
- ✅ Minimal code changes (refinement of existing)
- ✅ Users learn clear workflow: Generate → Schedule → Complete
- ✅ ScriptProperties sync across devices
- ✅ More stable keying (sheet row doesn't change)
- ✅ To Do List becomes explicit "working copy"

**Cons:**
- ❌ Still requires manual regeneration
- ❌ To Do List can still become stale
- ❌ Calendar section in To Do List still unused
- ❌ Doesn't solve all localStorage issues (just moves them)

**Implementation Complexity:** 🟡 Medium (1-2 weeks)

---

### Option C: Hybrid - Source Sheets + Persistent State Manager

**Concept:** Dialogs always read sources directly, but state is managed by a dedicated "Task State" system.

**Architecture:**
```
Source Sheets (read-only, authoritative)
    ↓
collectTasksForDialog() - Always reads fresh from sources
    ↓
enrichTasksWithState() - Joins with Task State
    ↓
HTML Dialogs (display combined data)
    ↓
User actions (schedule, notify, etc.)
    ↓
saveTaskState() - Updates Task State storage
    ↓
[NEW] Task State stored in:
    - ScriptProperties (for frequently accessed state)
    - Task State Log sheet (historical record)
```

**Task State Log Structure:**
| Timestamp | Employee | TaskType | ItemType | SourceSheet | SourceRow | Action | ScheduledDate | Notes |
|-----------|----------|----------|----------|-------------|-----------|--------|---------------|-------|
| 2026-01-28 14:32 | John Smith | Swap | Glove | Glove Swaps | 15 | NOTIFIED | NULL | Sent SMS |
| 2026-01-28 14:35 | John Smith | Swap | Glove | Glove Swaps | 15 | SCHEDULED | 2026-02-05 | Online class |
| 2026-02-05 10:15 | John Smith | Swap | Glove | Glove Swaps | 15 | COMPLETED | 2026-02-05 | Swap done |

**ScriptProperties Cache:**
```json
{
  "GloveSwaps_15": {
    "lastNotified": "2026-01-28",
    "lastScheduled": "2026-01-28",
    "scheduledDate": "2026-02-05",
    "classType": "Online",
    "status": "Completed",
    "completedDate": "2026-02-05"
  }
}
```

**Pros:**
- ✅ Source sheets always authoritative (no sync issues)
- ✅ State history preserved (audit trail)
- ✅ Can reconstruct state from log if ScriptProperties corrupted
- ✅ Clean separation: data vs. state
- ✅ Scalable (state log can be archived periodically)
- ✅ No localStorage (works across devices)

**Cons:**
- ❌ Most complex implementation
- ❌ Need state reconciliation logic
- ❌ More database-like design (higher maintenance)
- ❌ ScriptProperties has 500KB limit (need sharding strategy)

**Implementation Complexity:** 🔴 Very High (4-6 weeks)

### Phase 2: Improve Data Quality (Week 2)

#### 2.1: Simplify Phone Number Lookup

**File:** `Code.gs` → Create cache

```javascript
// Build phone map ONCE when dialog opens, not per-task
function getEmployeePhoneMapForTasks(ss) {
  var cache = CacheService.getUserCache();
  var cached = cache.get('employeePhones');
  if (cached) return JSON.parse(cached);
  
  var employeesSheet = ss.getSheetByName('Employees');
  var data = employeesSheet.getDataRange().getValues();
  var map = {};
  
  for (var i = 1; i < data.length; i++) {
    var name = String(data[i][0]).trim(); // Column A: Name
    var phone = String(data[i][4]).trim(); // Column E: Phone
    if (name && phone && phone.length >= 10) {
      // Store multiple keys for flexible matching
      map[name.toLowerCase()] = phone;
      // Also store "FirstName LastName" format
      var nameParts = name.split(/\s+/);
      if (nameParts.length >= 2) {
        var simpleKey = (nameParts[0] + ' ' + nameParts[nameParts.length - 1]).toLowerCase();
        map[simpleKey] = phone;
      }
    }
  }
  
  cache.put('employeePhones', JSON.stringify(map), 600); // Cache 10 minutes
  return map;
}
```

**User Impact:**
- Faster dialog loading
- Consistent phone matching
- Cache reduces sheet reads

```javascript
function checkToDoListFreshness() {
  var ss = SpreadsheetApp.getActiveSpreadsheet();
  var todoSheet = ss.getSheetByName('To Do List');
  if (!todoSheet) return {isStale: true, lastGenerated: 'Never', pendingTaskCount: 0};
  
  // Parse last generated timestamp from row 1
  var timestamp = todoSheet.getRange(1, 10).getValue();
  var generatedDate = new Date(timestamp);
  var hoursSinceGen = (new Date() - generatedDate) / (1000 * 60 * 60);
  
  // Check for new pending tasks in source sheets
  var tasksByLocation = collectAndGroupTasks(ss);
  var pendingCount = countTasks(tasksByLocation);
  
  return {
    isStale: hoursSinceGen > 24, // Stale if > 24 hours old
    lastGenerated: Math.floor(hoursSinceGen / 24) + ' days ago',
    pendingTaskCount: pendingCount
  };
}
```

**User Impact:**
- Proactive alerts for stale data
- One-click refresh
- Know when regeneration is needed

function checkAndMigrate() {
  // Check if user has old localStorage data
  var hasOldData = localStorage.getItem('rubberTracker_personalChecklist') !== null;
  
  if (hasOldData) {
    // Read all localStorage
    var oldData = {
      checklist: JSON.parse(localStorage.getItem('rubberTracker_personalChecklist') || '[]'),
      notified: JSON.parse(localStorage.getItem('rubberTracker_notifiedTasks') || '{}'),
      scheduled: JSON.parse(localStorage.getItem('rubberTracker_scheduledTasks') || '{}'),
      office: JSON.parse(localStorage.getItem('rubberTracker_officeTasks') || '{}'),
      classType: JSON.parse(localStorage.getItem('rubberTracker_classTypeTasks') || '{}')
    };
    
    // Send to server for migration
    google.script.run
      .withSuccessHandler(function() {
        // Clear old localStorage
        localStorage.removeItem('rubberTracker_personalChecklist');
        localStorage.removeItem('rubberTracker_notifiedTasks');
        localStorage.removeItem('rubberTracker_scheduledTasks');
        localStorage.removeItem('rubberTracker_officeTasks');
        localStorage.removeItem('rubberTracker_classTypeTasks');
        
        showToast('✅ Data migrated to server storage');
        loadTasks(); // Reload with new data source
      })
      .migrateUserData(oldData);
  }
}

## Questions for Discussion

### 1. To Do List Sheet Purpose

**Question:** Should To Do List be:
- **A) Working schedule** (users edit it, save back to sources)
- **B) Read-only snapshot** (regenerated frequently, don't edit)
- **C) Eliminated** (dialogs read sources directly)

**My Recommendation:** B - Read-only snapshot with clear "Last Generated" timestamp

### 2. Personal Checklist Scope

**Question:** Should Personal Checklist:
- **A) Only store user-added manual items** (remove cert tasks from it)
- **B) Be a filtered view of all tasks** (no separate storage)
- **C) Keep current hybrid approach** (some localStorage, some server)

**My Recommendation:** A - Separate "My Tasks" (manual) from "My Certs" (filtered view)

### 3. Task Completion Flow

**Question:** When user marks task complete:
- **A) Update source sheet immediately** (current)
- **B) Update To Do List only, sync to source on "Generate"** (batched)
- **C) Create "Completed Tasks" log, don't modify sources** (audit trail)

**My Recommendation:** A for now, C as future enhancement

### 4. Phone Number Storage

**Question:** Should phone numbers be:
- **A) Always looked up from Employees sheet** (current)
- **B) Cached in task objects** (faster but stale)
- **C) Copied to To Do List during generation** (denormalized)

**My Recommendation:** C - Copy to To Do List, makes it self-contained

### 5. State Persistence Strategy

**Question:** Should we:
- **A) Move entirely to ScriptProperties** (recommended Phase 1)
- **B) Create Task State Log sheet** (Option C from above)
- **C) Use both** (ScriptProperties for cache, sheet for history)

**My Recommendation:** Start with A, add B later for audit trail
